# Intent: Show the marketplace preview image in the panel

## Problem

The marketplace website (plugins.omarchy.org) shows a screenshot for every
plugin, so you can see what it looks like before installing it. The Plugin
Browser panel shows only text: the name, description, badges and verdicts.
Choosing a bar widget or a panel from a description alone is guesswork, and
it pushes people back to the website, away from the audited install path.

The images are already described in the data the panel downloads. The
catalog (`https://plugins.omarchy.org/catalog.json`) carries, for **3379 of
3969** plugins:
- `previewImage` (1600×900) and `previewThumbnail` (720×405), as paths
  relative to the site, for example
  `assets/img/plugins/5-crmne-omarchy-hyprmoncfg-card.webp`;
- the matching width and height fields.

Checked: both URLs answer `200` with `image/webp`, at 21 KB for the thumbnail
and 68 KB for the detail image. The shell can already decode WebP:
`qtimageformats` with `libqwebp.so` and `libwebp` are in quickshell's
closure.

## Proposed outcome

- **Opening a plugin's details shows its preview image** at the top of the
  detail pane, above the description. It is the website's own screenshot.
- **Only the plugin you open is fetched,** never the whole list. The list
  stays text, so it opens as fast as it does now.
- **Plugins without a preview** (about 590) show the detail pane exactly as
  today, with no broken image and no empty box.
- **The image arrives without blocking.** The text shows at once, and the
  image appears when it is ready. While fetching, or if the fetch fails, the
  pane shows text only, and at most a quiet note.
- **Fetched images are cached,** so reopening a plugin, or reopening the panel,
  shows the image instantly and offline.
- **The keyboard flow does not change.** No new key is needed to see the
  image. An optional key to view it larger is a question for the spec.

## Affected users and systems

- Everyone who uses the Plugin Browser panel (this repo, 0.5.0).
- This repo:
  - `lib/catalog.sh` gets a bounded preview download, and `list` passes the
    preview path through;
  - `Model.js` builds and validates the URL and argv, with node tests;
  - `BrowserState.qml` runs the fetch;
  - `BrowserView.qml` draws the image;
  - README and CHANGELOG.
- The long-running `omarchy-shell` process, which would now decode images.
- The flake's `plugin` package and its checks: the files are the same, but
  their behaviour changes.

## Constraints

- **The shell never fetches from the network itself.** It must not decode an
  image it has not had checked. A helper script downloads the file; the shell
  only reads a local, already-verified file. Image decoders are a classic
  attack surface, and this process holds the whole desktop.
- **Fixed host.** Previews come only from `https://plugins.omarchy.org/`.
  - The path comes from the catalog, but it is checked:
    `assets/img/plugins/<safe-name>.webp`, with no `..`, no scheme and no
    query string.
  - Any other host or shape is refused.
- **Bounded:**
  - a size ceiling far above the real files (they are under 100 KB; the
    ceiling is 2 MB);
  - a deadline;
  - the download must be RIFF/WEBP (or PNG) by its magic bytes, not trusted
    by content-type alone;
  - an owner-only cache under `~/.cache`, written atomically, as the catalog
    is.
- **Nothing blocks the UI.** Fetching runs in a `Process`, decoding is
  asynchronous, and a slow or failed fetch is invisible except as "no
  image".
- **Privacy.** Fetching a preview tells plugins.omarchy.org which plugin you
  opened. That is the same site the catalog comes from, and only a plugin you
  open is fetched. The README says so, and there is a switch to turn
  previews off.
- **Consistency.** The same PATH, argv and plain-text rules as the rest of
  the panel, and the flake's `plugin` package still passes nixarchy's checks.

## Open questions

- **Thumbnail or full image?** The proposal is the 720×405 thumbnail in the
  pane: small, and enough at the panel's size. Whether a key such as `v`
  opens the 1600×900 image larger is for the spec to decide, and YAGNI says
  leave it out.
- **Off switch.** The proposal is a plugin setting, `previews: true` by
  default, in the manifest's defaults.
- **Cache lifetime.** The proposal is to keep previews until the catalog says
  the path changed. The file name changes with the image, so no expiry is
  needed; the cache is pruned when it passes a size cap.
