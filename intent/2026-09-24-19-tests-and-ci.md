# Intent: Run the tests on every pull request, and test the audit's gates

## Problem

The repository has four self-checks in `tests/`, and they all pass locally.
Nothing runs them for a pull request, and the code that matters most for
security has no tests at all. From the 2026-09-24 review (items 17, 18, 22):

- **No CI for the code.** The only workflow is `.github/workflows/pages.yml`,
  and it runs only when `docs/**` changes. A pull request that breaks
  `lib/`, `bin/`, the QML or `flake.nix` gets no signal. `nix flake check` is
  never run by anything but a person.
- **The flake check covers half the tests.** `checks.default` runs
  `tests/scan-nix.sh` and `tests/model-check.mjs`. It leaves out:
  - `tests/preview.sh`, which already runs hermetically and could go in as it
    is;
  - `tests/catalog-list.sh`, which cannot run in the sandbox because
    `lib/catalog.sh` pins `PATH` to `/run/current-system/sw` and friends.
- **The audit's gates are untested.** `bin/omarchy-plugin-audit` is the
  safety boundary, and none of its refusals has a test:
  - exit 20 when the FIND or VALIDATE stage fails;
  - refusing a local plugin directory that contains symlinks;
  - the `AUDIT_STAGE_DEADLINE_SEC`, `AUDIT_STAGE_MAX_BYTES` and
    `AUDIT_STAGE_MAX_FILES` limits;
  - hostile catalog rows and a spoofed VALIDATE result.

  All of these can be exercised offline, with `CATALOG=<fixture>` and a local
  directory as the target.
- **Other gaps.** `lib/update.sh` has no test. The Home Manager module
  (`homeManagerModules.default`) is never evaluated by a check, so a typo in
  it would reach a user's rebuild first. Nothing checks that the flake's
  hand-kept `files`/`dirs` list matches the runtime files in the repository;
  a new QML file left off the list would ship a broken plugin.
- **The Pages workflow is loosely pinned.** Its actions are pinned by tag,
  not by commit SHA; `actions/checkout` keeps the default
  `persist-credentials: true`; and the `concurrency` group `pages` is shared
  by pull requests and `master`, so a pull request can queue behind, or
  delay, a deploy.

## Proposed outcome

- **Every pull request and every push to `master` runs a code CI workflow.**
  It runs `nix flake check`, and whatever tests cannot run inside the
  sandbox, and a red result blocks the merge.
- **`nix flake check` runs every test that can be hermetic,** including
  `tests/preview.sh`, the new audit-gate tests, an evaluation of the Home
  Manager module, and a check that the packaged file list matches the
  repository.
- **`tests/catalog-list.sh` runs somewhere automatic,** in the sandbox if it
  can be made to, otherwise as a CI step.
- **The audit's gates each have a test** that fails if the gate is removed:
  exit codes, symlink refusal, the three stage limits, and hostile or spoofed
  input.
- **`lib/update.sh` has a test** for its decisions.
- **One shared test harness,** so the fix issues can add their regression
  tests in the same shape, and one command runs everything locally.
- **The Pages workflow is hardened:** actions pinned by SHA,
  `persist-credentials: false`, and a concurrency group that does not let a
  pull request hold up a deploy.

## Affected users and systems

- Contributors and reviewers: every pull request gets a result.
- This repository:
  - a new workflow under `.github/workflows/`;
  - `.github/workflows/pages.yml`;
  - `flake.nix` (`checks`);
  - `tests/`: new audit and update tests, and a shared harness;
  - possibly a small change to `lib/catalog.sh` so that `catalog-list.sh` can
    run in the sandbox. The spec decides whether that is worth it.
- GitHub repository settings: branch protection, to make the check required.
- Users of the plugin: none directly. They get fewer regressions.

## Constraints

- **Offline and hermetic where possible.** No network inside a nix check.
  The tests use fixture catalogs and local plugin directories, never the live
  marketplace or GitHub.
- **Tests must not weaken what they test.** The audit's pinned `PATH`, its
  sandbox and its limits stay as they are. Tests reach them through the
  existing environment knobs (`CATALOG`, `AUDIT_STAGE_*`, a local target),
  not through new test-only bypasses in the production code.
- **Scope.** The fixes in #15, #16, #17 and #18 each add their own
  regression tests. This issue owns the CI workflow and the shared test
  harness, and tests for behaviour that already exists. It does not fix
  those bugs.
- **Keep the tests plain:** bash and node, as they are now. No test
  framework.
- The manual and non-Nix install is not changed.
- The Pages site keeps building and deploying exactly as it does now.

## Open questions

- **Runners:** GitHub-hosted `ubuntu-latest` with Nix installed by an action,
  or a self-hosted runner on p620? Hosted is simpler and isolated;
  self-hosted is faster and has the nix store warm, but runs PR code on a
  home machine.
- **aarch64:** the flake declares `aarch64-linux`. Should CI build and check
  it too (hosted ARM runners or emulation), or only `x86_64-linux`?
- **Binary cache:** add a cache action (for example magic-nix-cache or
  Cachix) or accept cold builds? The closure is small.
- **Dependabot** for GitHub Actions, to keep the SHA pins current? Proposal:
  yes, actions only, weekly.
- **`catalog-list.sh`:** make `lib/catalog.sh`'s `PATH` overridable for the
  sandbox, or run that test as a plain CI step outside Nix?
- **Branch protection:** make the new check required on `master`? Proposal:
  yes, once it has been green for a few pull requests.
