# Intent: Run inside the Omarchy shell as a keyboard-driven panel with its own keybinding

## Problem

The plugin browser does not feel like the other nixarchy plugins:

- **It lives outside the shell.** The bar button (`BarWidget.qml`) only opens
  a terminal, and the whole UI is a `gum` TUI in that terminal
  (`bin/omarchy-plugin-browser`). It looks different from the rest of the
  desktop and takes a second window.
- **It has no keybinding.** The only way in is clicking the bar button, and
  only once the widget has been added to the bar.
- **It is not consistent with its neighbours.** `nixarchy.podman` and
  `nixarchy.devenv` run inside the shell as QML. Each has:
  - a full-screen, keyboard-first surface (`Menu.qml`), opened with
    `omarchy-shell shell toggle <id> '{}'`;
  - the same view in a bar popup (`Panel.qml`);
  - a state object that runs their CLI through `Process`;
  - a `?` shortcut sheet (`ShortcutSheet.qml`);
  - a `*-binds.lua` keybinding file that `~/.config/hypr/bindings.lua` loads
    with `pcall`.

  Users who learned those plugins' keys cannot reuse them here.

## Proposed outcome

- A keybinding opens a full-screen **Plugin Browser** surface over whatever
  the user is doing, the same way Super+Alt+E opens Dev environments. Pressing
  it again, or Esc, closes it. The same view is available from the bar
  button's popup and from a menu row.
- **Everything is keyboard-driven:**
  - type to search the marketplace (name, author, tag, category);
  - arrow keys or j/k to move;
  - Enter to open a plugin's details;
  - single keys to audit it, run the NixOS check, explain or fix with the
    agent, copy the install command, or open the repo;
  - `?` for the shortcut sheet.

  The mouse works but is never needed.
- **The panel shows the results inside the shell:** the verified, snapshot and
  unverified badge, the security verdict with its findings and capabilities,
  and the **NixOS verdict** with its findings.
- **The existing tools still do the work.** The panel shows what
  `omarchy-plugin-audit --json` reports and never re-implements the scan. The
  sandbox, pinning, fail-closed behaviour and the explain/fix safety rules
  stay exactly as they are.
- **Anything that needs a terminal still gets one.** The interactive agent
  session and install confirmations open in a terminal, started from the
  panel.
- **The keybinding** ships as a `*-binds.lua` file, as `nixarchy.devenv` does.
  It shows up in Omarchy's key bindings menu (Super+K).
- **It replaces Add Plugin in the nixarchy menu.** When this is done, the
  *Setup → Plugins… → Add Plugin* row (`setup.plugin.add`) opens the Plugin
  Browser surface instead of `omarchy-plugin-add` in a terminal. Adding a
  plugin from the menu then always goes through search, audit and the NixOS
  check. Its label and position stay recognisable. Enable, Disable, Clone and
  Remove are unchanged.

## Affected users and systems

- nixarchy users of this plugin, and anyone who uses the keyboard-first
  nixarchy panels.
- This repo:
  - `manifest.json` (it gains `kinds: menu`).
  - New QML files, following the podman/devenv layout: a `Menu.qml` surface, a
    shared view, a state object, a shortcut sheet, and a keybinding `.lua`.
  - `BarWidget.qml`: the button opens the shared view.
  - `install.sh`, `uninstall.sh`, `README.md`, `CHANGELOG.md`.
- `~/.config/hypr/bindings.lua`. It is the user's own file, so the change is
  one `pcall(require, …)` line, added only with consent.
- The nixarchy menu's `setup.plugin.add` row. The generated defaults file is
  `$OMARCHY_PATH/default/omarchy/omarchy-menu.jsonc`, and rows are overridden
  by id from `~/.config/omarchy/extensions/omarchy-menu.jsonc` or declared
  through `programs.nixarchy.menu.extraEntries`.
- It relies on `omarchy-shell` (IPC, `shell toggle`), Quickshell's `Process`,
  and the existing `omarchy-plugin-audit` and `nixarchy-plugin-fix`.

## Constraints

- **Security posture must not regress.** It is the whole point of this tool:
  - Plugin code is never loaded, imported or executed in the shell, and the
    panel never parses a plugin's code, only the catalog and the audit's JSON.
  - The catalog stays size-bounded and is only ever read as data.
  - Marketplace text is shown as plain text, never rich text or markup, so a
    plugin description cannot inject UI.
  - Processes are started with fixed argv and absolute paths, with no shell
    strings and no PATH lookups, as in `BarWidget.qml` today.
  - Nothing is enabled automatically. Install stays disabled-by-default and
    goes through the audit.
- **The shell is long-lived and shared.** Work stays off the UI thread: the
  catalog is about 8 MB, so filtering must not stall the bar. A failure in
  the panel must not take the shell down.
- **Consistency with podman and devenv.** Same file roles, same key
  conventions (j/k, Enter, Esc, `?`), same `omarchy-shell shell toggle`
  entry, same `pcall`-loaded binds file.
- **Keep the CLIs working on their own.** `omarchy-plugin-browser`,
  `omarchy-plugin-audit` and `nixarchy-plugin-fix` remain usable from a
  terminal, and the TUI is not removed in this task.
- **Declarative-friendly.** The keybinding file follows the devenv approach,
  so a Home Manager option can write it later. This repo does not edit
  `bindings.lua` without asking.

## Open questions

- **How the menu row is replaced.** Either an entry in the user's
  `~/.config/omarchy/extensions/omarchy-menu.jsonc` (by id, with consent,
  like `bindings.lua`), or declaratively through
  `programs.nixarchy.menu.extraEntries` in the flake, or both. This is for
  the spec, after checking which of them can override an existing id.

- **Keybinding.** The proposal is **Super+Alt+U** ("plUgins"), which is free
  in the current Lua bindings. Super+Alt+P, E, N, A, B, Q and V are taken.
- **Where the agent session runs.** The proposal is a floating terminal
  (`omarchy-launch-tui`), because the agent and gum are interactive. The panel
  shows the result when the terminal closes.
- **The gum TUI.** Keep it as the terminal fallback (proposed), or retire it
  once the panel covers everything?
- **Bar widget.** Keep the button, now opening the popup view, as podman and
  devenv do (proposed), or rely on the keybinding and the menu row only?
