# Intent: Package the plugin as a flake for declarative install on nixarchy

## Problem

The plugin has no `flake.nix`. The only ways to install it are by hand:
`./install.sh --plugin` or `omarchy plugin add <repo>`, which clones HEAD into
`~/.config/omarchy/plugins/`. On nixarchy that means it:

- **cannot be pinned or reproduced.** There is no locked revision, and a new
  machine or a reinstall does not get it back.
- **cannot go into the nixarchy configuration** with the rest of the desktop.
  The Add Plugin menu row and the Super+Alt+U keybinding are already declared
  in `nixos_config` (#1971), but they point at a plugin that is not declared
  anywhere.
- **cannot be tested the way it will be used.** Once the panel passes its
  desktop checks (#4, G1), it should reach p620 and razer through the same
  flake as everything else.

nixarchy already has the declarative path. The Home Manager option
`programs.nixarchy.plugins.<name>.src` takes a directory with a `manifest.json`
(a flake input, a `fetchgit`, or a path) and links it read-only into
`~/.config/omarchy/plugins/<id>`. It validates the plugin at build time, so a
broken plugin fails the rebuild instead of failing after login
(`modules/home.nix`, nixarchy `99223857`).

Checking this repo against that option found two blockers:

1. **nixarchy's build check would reject the plugin as it is.** The check fails
   any plugin with `\bpacman\b|\byay\b` on a non-comment line of a `.qml`,
   `.js`, `.sh` or `.bash` file, because such a plugin would try to run a
   package manager NixOS does not have. This repo has three such lines, and
   none of them runs pacman:
   - `lib/omarchy-plugin-scan.sh:164` and `:228`: the scanner's own patterns
     for spotting pacman in *other* plugins;
   - `tests/scan-nix.sh:21`: a test fixture.

   The check cannot tell a detector from an invocation.
2. **Parts of the plugin assume a writable git checkout.**
   - The bar's update alert runs `omarchy plugin update`, which needs a `.git`
     folder. A store path has none, and a flake install updates through the
     flake lock.
   - `install.sh` symlinks the CLI tools into `~/.local/bin` and registers the
     widget with `omarchy plugin add`. Neither step makes sense when Home
     Manager provides the plugin.
   - The tools (`omarchy-plugin-audit`, `omarchy-plugin-browser`,
     `nixarchy-plugin-fix`) are then not on `PATH` for terminal use at all.

## Proposed outcome

- **The repo is a flake.** A nixarchy user can add it as an input and install
  it with:

  ```nix
  programs.nixarchy.plugins.plugin-browser.src = inputs.nixarchy-plugin-browser;
  ```

  or with a path or output the flake provides. Home Manager's build-time check
  passes, and the plugin appears in `~/.config/omarchy/plugins/` as a
  read-only store link, like `nixarchy.devenv` and `nixarchy.microvm`.
- **The CLI tools are installable from the same flake,** for terminal use.
- **The panel, the audit, the NixOS check and the agent hand-off work the same
  from a store install.** They already run everything through their own folder,
  and they write only to `~/.cache`, `~/.local/state` and `~/.local/share`.
- **Updates behave sensibly for a store install.** The update alert does not
  offer an `omarchy plugin update` that cannot work, and `nix flake update`
  is the update path.
- **The manual route still works** for people not on Nix: `./install.sh` and
  `omarchy plugin add`.
- **`nixos_config` can switch from "the plugin must be installed by hand" to
  declaring it.** That is a separate change in that repo, after testing.

## Affected users and systems

- nixarchy users who want this plugin declared, including p620 and razer.
- This repo:
  - new `flake.nix` and `flake.lock`;
  - the scanner and tests, for the pacman check;
  - `lib/update.sh` and `BarWidget.qml`, for update behaviour on a store
    install;
  - `install.sh` and `README.md`.
- nixarchy's `programs.nixarchy.plugins` option and its build check. These are
  used as they are, not changed.
- `nixos_config`: later, a flake input and one `programs.nixarchy.plugins`
  line. That is not part of this repo's work.

## Constraints

- **The security scanner must lose nothing.** Whatever satisfies nixarchy's
  pacman check must still detect pacman and yay in *other* plugins, and the
  tests must prove it.
- **No workaround that fools the check without fixing what it is for.** The
  check exists to stop a plugin from running a package manager. The plugin
  must honestly not do that, and the change should read as intent, not
  evasion.
- **A read-only store install must work:** no writes into the plugin's own
  folder, no reliance on `.git`, and no exec bit needed (everything already
  runs through `bash <file>`).
- **Follow nixarchy's flake conventions** where they exist (the devenv and
  microvm plugins), and add nothing speculative: no NixOS module and no
  overlay unless a consumer needs one.
- The manual and non-Nix install keeps working.

## Open questions

- **Which output should `programs.nixarchy.plugins.*.src` use?** The raw flake
  source (`inputs.x`) is the simplest. A filtered `packages.plugin` that leaves
  out `tests/` and the `intent/`, `spec/` and `plan/` docs is tidier, and it
  also keeps the test fixture out of the check. The proposal is a filtered
  package; the spec will compare them.
- **How to satisfy the pacman check.** Options include rephrasing the three
  lines so the literal word is not a whole word (for example `pac[m]an` as a
  regex), leaving tests out of the installed plugin, or both. The spec will
  choose the one that keeps the detection identical and reads clearly.
- **The update alert on a store install:** hide it, or point it at
  `nix flake update`? The proposal is to detect a read-only or git-less
  install and show the flake route instead of the Update… button.
